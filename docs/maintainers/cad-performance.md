# CAD performance baseline

`npm run cad:benchmark` measures the CAD kernel and sketch solver on fixed workloads and writes JSON reports to `tmp/cad-benchmark/`. Add `-- --quick` for a shorter run or `-- --runs N` to change the sample count (a positive whole number, default 7). `-- --group legacy` selects the original kernel, solver-scaling and drag-preview groups; `-- --group solver-workloads` selects the public-boundary native solver workloads below, which compared PlaneGCS and native until 0.0.757. The default, `-- --group all`, runs both. `-- --group preview` runs only the legacy drag previews. From 0.0.761 the npm script runs the benchmark bundled by Vite as the application is built (`scripts/run-bundled.mjs`), and each report records its `runner`. tsx wraps every function to keep its name, which made the medians of the same drag previews 5 to 12% slower in one run against each of two bundled runs, so compare only reports of the same runner. A solver-workloads run directory records its runner, and a run with another runner neither resumes nor aggregates into it. Cold solver probes still start fresh processes through tsx, as before. No browser or dev server is needed. Use it before and after a change that claims a speed or memory improvement, and record both reports in the pull request.

## Workloads and correctness

`src/features/cad/benchmark/cadBenchmarkCases.ts` defines the workloads. Kernel cases are complete documents with edit steps and analytic expected volumes. `cadBenchmarkCases.test.ts` builds every step in the normal Vitest suite, so a case that stops producing its analytic geometry fails CI instead of producing misleading timings. The script also marks such a step `INCORRECT` and exits non-zero.

| Case | What it isolates |
| --- | --- |
| `plate-hole-pattern` | Ordinary sketch, extrude, linear pattern and boolean cut; the width edit invalidates every feature. |
| `gear-and-plate` | A gear plugin profile (hundreds of faces) beside an independent holed plate. The plate edit rebuilds the unchanged gear. `affectedBodies` is the plate alone, with its unchanged hole pattern, and has its own analytic volume. |
| `box-fillet-all-edges` | Rolling-ball fillet of all twelve box edges and a radius edit. |

Solver workloads are independent, fully constrained rectangles (4 lines and 7 relations each). The connected capacity workload instead places each rectangle by two axis distances from the previous one, so all rectangles form one solver group. The drag preview uses documents with 1, 4, 8 and, from 0.0.761, 32 independent graph sketches of 10 rectangles. The first rectangle of the first sketch has its fixed corner released, and one corner move is prepared through `prepareCadEdits`, as a sketch drag preview does. The suite checks that the rectangle follows the drag and that every other sketch is unchanged. From 0.0.763 each size also runs with an extrude after every sketch, so a preview's parse checks that each extruded sketch still has regions; the drag keeps every extrude. A dependent workload adds a second sketch that uses the first rectangle's bottom edge. It drags the referenced rectangle, which must re-solve the dependent, and a second released rectangle, which must not.

## Metrics

- `buildMs`: uncached `buildCadKernelModel` of the full document. `coldMs` is the first build of the first step in a fresh module.
- `shippedEditMs`: the previous step followed by this step through `createCadKernelRuntime`, which caches only a whole document.
- `affectedBodiesMs`: uncached build of only the bodies the edit changes, including unchanged inputs they need. It is sampled alternately with `shippedEditMs` so both see the same clock speed. A rebuild that reuses unaffected bodies should take no longer than this; it can be faster by also reusing unchanged inputs.
- `payload`: triangles, plain-array numbers and JSON size of the build result that crosses the worker boundary.
- `mainThread`: `structuredClone` of the reply, `isCadKernelReply` validation and `prepareCadMeshDisplay` for every mesh. The app pays these on the main thread for each build.
- `memoryBytesAfterRebuilds`: OpenCascade linear-memory capacity after 1, 10 and 50 edits through one shipped runtime, alternating the case steps so each edit replaces the cached model. WASM memory grows but never shrinks, so this is a high-water mark. Each case runs in a fresh OpenCascade module, so its numbers do not depend on the cases before it.
- Solver `scaling`, `drag`, `dragPreview` and `capacity`. Each drag preview reports `solvesPerPreview` (solver calls for one preview), `prepareMs` for the whole preparation and `solverCallMs` for the solver calls inside it (constraint compilation, the native solve and reply validation); the difference is document parsing, reference refresh and checks. From 0.0.761, `documentParseMs` times one `parseCadDocument` of a detached copy of the prepared document, after every timed preparation so its allocations stay out of them, which checks every feature as a parse of a document it has not accepted does, and `documentJsonBytes` gives that document's size. From 0.0.763 `dragPreview.padded` reports the sizes with an extrude after every sketch, as `dragPreview.independent` does without them. From 0.0.764 each drag preview also reports `viewportReferencesMs`: `prepareCadViewportReferences` of each prepared document, after that of the document it was prepared from, as the workbench prepares references when a preview replaces its document. Capacity uses a fresh runtime per size, because PlaneGCS's fixed memory aborted with OOM. It probes independent and connected rectangles separately, records each size's native parameters and constraints, and reports the largest rectangle count that solved and the first that did not, with its rejection reason. From 0.0.757 these run on the native runtime the app uses and `solver.initMs` times compiling the module and one instance. Before, they ran on PlaneGCS, and from 0.0.750 a `nativeFirst` section repeated `scaling` and `dragPreview` through the native-first runtime.
- `cpuCalibrationMs`: a fixed JavaScript loop timed before and after each measurement group: full builds, edits and main-thread work for each kernel step, and each solver size, the solver drag and each drag-preview size. Laptops reduce clock speed under sustained load; the development host below ran the same loop 3.5 times slower after about three seconds. The script marks a group `THROTTLED` when its calibrations differ by more than 1.5 times and warns when they do across the run. Use only unthrottled groups, compare groups with similar calibration, and never compare across hosts.

## Findings that set the order of work

1. Drag previews re-solve every graph sketch in the document, so preview cost grows with unrelated sketches.
2. PlaneGCS aborts on a few hundred constrained entities because its memory cannot grow; the worker reports the raw abort text and restarts. Measured with one solver group, the abort depends on unfixed parameters times constraints: 760 x 760 solved and 800 x 800 aborted for independent rectangles, while a connected chain solved 800 x 800 and aborted at 1000 x 1000.
3. Every edit rebuilds every feature. Unchanged expensive bodies dominate edits of cheap ones. OpenCascade memory already grows from 100 to 127 MiB between the 10th and 50th edit of the holed plate, so a feature cache must show no more growth than that over the same 50 edits.
4. Build results cross the worker as plain arrays (1.1 MiB JSON for 5.8k triangles) and are validated and prepared for display again on the main thread. That costs about 5 ms a build here, so it is a payload and memory cleanup, not the main latency.

Proposed order: solve only edited sketches and their reference dependents, then solve independent sketch components separately with a clear limit message; incremental feature rebuilds keyed by a chain hash with bounded memory after 50 rebuilds as a gate; typed-array transfer with display preparation in the worker. Rust or kernel replacements are considered only where this benchmark shows the remaining time is inside the native kernel or solver.

From 0.0.762 `parseCadDocument` remembers every feature of a document it accepted. Every check that reads the document still runs over all its features, among them parameters, references between features, ids and history order, so a document is accepted or rejected with the same error as before. - A feature a revision did not change now keeps its object, where each parse used to make a new one. The feature and profile forms therefore compare revisions, not objects, and still start again from each revision of the part that holds what they edit. The sketch canvas forgets the points the pointer rested on at each revision and parameter change, since their positions can move while the sketch keeps its object.

## Native sketch solver

`packages/sketch-solver` is our own Rust constraint solver, compiled to a WebAssembly module with no dependencies (92 kB, 33 kB gzip, at 0.0.739). From 0.0.739 it was built, tested and compared with PlaneGCS; from 0.0.746 the app solved with it first; from 0.0.757 it is the app's only sketch solver.

- `compileCadSketchEquations` turns a sketch into scalar parameters and twelve kinds of scalar equation, and the module solves them.
  - Each connected group of unknowns gets its own damped Gauss-Newton solve, with exact gradients from dual numbers.
  - Each equation is divided by its gradient norm over the unknowns, so every residual reads as the distance they must move.
  - Each step comes from a Givens QR of the weighted Jacobian, not the normal equations, so roundoff does not move the free directions of an under-constrained sketch.
  - From 0.0.740 the QR is sparse:
    - Rows keep their authoring order. Columns take a minimum-degree order fixed by the structure, so a chain of profiles fills like a band.
    - Each damping trial refactors from `sqrt(mu) I` and then rotates in the Jacobian rows. A row meeting a diagonal-only row carries on with only its own entries, so most rows stop near their own length. Rotating the damping in after the Jacobian, as MINPACK does, would run each damping row down the whole elimination tree: about 300 million updates per trial for a 5,000-link chain.
    - In that order, the motion along directions the Jacobian leaves free depends on roundoff whenever dependent rows disagree within a step. Conflicting relations always do. Redundant ones also do before the solve converges, when their linearizations are different functions of the same motion: an angle of 90° plus a perpendicular relation on the same lines, far from the origin, moves a free midpoint by about 0.4 µm. The same relation entered twice does not, because its rows agree exactly. Both kinds of sketch are rejected by diagnosis. From 0.0.742 rows dependent at the start stay out of the first solve, which removes this drift (see below).
    - For sketch-like structure, where profiles join in chains and trees and shared parameters such as a radius are eliminated last, time and memory grow about linearly with the size of a group. A group whose columns are all coupled at random fills almost completely, as in a dense factorization.
  - Native code cannot be interrupted, so each group has limits:
    - The ordering gives the exact fill of the factor before any numeric work. A group above 2,000,000 entries (about 32 MiB) is left in place. The ordering stops as soon as the fill so far, plus the edges still present and the diagonals still to come, passes that limit, so its own memory stays within about twice the limit.
    - The ordering, and every rotation after it, count the entries they write against 400,000,000. Rotations check the count before every step, so a group stops within one step of the limit, where it got to. From 0.0.742 a group's diagnoses continue from the count its solve reached, and a diagnosis that runs out is `unavailable`. Labelling across groups has its own allowance of the same size.
    - In a native probe, random groups of 2,000 to 4,200 unknowns whose factors would be dense are refused in under half a second.
    - Either reports `too-large`. This replaces the PlaneGCS limit of 500,000 unfixed parameters times equations, which a chain of 89 rectangles already exceeds.
  - Convergence is judged apart from that weighting:
    - each residual must be within the driver tolerance in millimetres;
    - each direction error must be within 1e-12 radians, or the roundoff of its coordinates at the far end of the longer line.
  - The solver status only reports convergence of its own equations. As with PlaneGCS, the graph checks decide whether a result is accepted, including degenerate lines, angle sectors and the distance between collinear segments.
  - Iteration continues to roundoff, because the graph checks require coincident points to agree within 8 ulp of their coordinates.
  - From 0.0.743 polishing past acceptance stops at the second step in a row that gains less than a quarter of its prediction and less than `1024 epsilon` of the cost. Such a step moves only roundoff: a direction whose roundoff floor sits above the polish level, as in the die after its slot radius grows 0.5 mm, otherwise kept the loop taking them until they vanished, 50 iterations instead of 6. Both conditions are needed. Leaning guides that converge linearly gain what they predict, and a point near a tangency can gain 8% of the cost with a ratio of 0.08. One such step can still be real, as when a point drags its own guide, so a single one does not stop polishing.
- From 0.0.749 a group that converged with freedom left, diagnosed without conflicts or redundancies, moves on toward the solution nearest its start values. Damped Newton steps reach a solution but not the nearest one where relations bend: a direction residual is a normalized sine, so its step moves a point across its line rather than straight onto the line it must lie on. Applying Parallel between a free point's line and a horizontal reference moved the point from (35, 15) to (35.714, 20) instead of (35, 20). Each of at most four rounds, sharing the 100-iteration allowance, solves the linearized relations for the least change from the start, `min |z|` with `J z = J (x - start) - r`, converges again from `start + z` and stands only when every row is still accepted and the group ended nearer its start. That reaches the nearest solution when the relations are linear in the moved unknowns and only brings the group nearer otherwise. The moved group is diagnosed again, and unless its rank and its lack of witnesses are unchanged the first diagnosed solution is kept: a point held 1 mm from two points 2 mm apart lies on a tangency, and a nearer solution there read as rank-unclear. Reported iterations include the correction. Well-constrained groups, such as the die, and drags skip it; a group with freedom left pays about one factorization more, and a second diagnosis when it moved. A group whose rank is too close to call skips it too. Measured for 0.0.754 over the 1,539 native solves of the full Vitest suite, the only such solves that were not drags were nine in the tangency lifecycle, a point held by a circle and a line at their tangency with nothing free and so nothing to move; the rule stays until a sketch shows otherwise.
- From 0.0.742 the module diagnoses every solve, as PlaneGCS does (`src/diagnose.rs`, wire protocol 2):
  - Each equation carries the tag of its source constraint (coincident, midpoint and symmetric relations have two equations) and a temporary flag for drag targets, which are solved but not diagnosed.
  - **Rows dependent at the start.** Before each group is solved, its lasting rows go into a rank-only factor at the input values. Rows within `TAU = 1e-10` of the span of earlier ones (once each row has unit norm) stay out of a first solve. That result stands if every row is then accepted. Otherwise the group is restored and solved with every row, sharing the 100 iterations and the work limit. Unclear rank or an exhausted budget solves every row.
  - **Diagnosis at the result.** Rows go in authoring order into an undamped sparse factor in the solve's column order. A dependent row gets a witness: the earlier rows that reproduce it. Its coefficients come first through the same factor, by seminormal equations corrected from what the combination still misses until the correction stops shrinking it; this stays as sparse as the solve. The factor's pivot columns can be far worse conditioned than the rows themselves, so a combination found this way that reproduces the row is a witness, but one that does not proves nothing. The rows it chose are then fitted on their own by least squares: their transpose is factored by rotations and corrected the same way. A value shared by many rows makes that factor dense, so it is held to the group's fill limit, and a fit that would pass it leaves the diagnosis `unavailable`; 3,200 midpoints around one free value are diagnosed through the solve's factor in about 2 MiB. Coefficients and misses are kept in twice the working precision (error-free sums and products), so a combination found within the distance is, and terms near 1e6 that cancel neither hide a real miss of 1e-9 nor make one up. A row within `TAU` of the span can lean on a nearly parallel one by up to about `epsilon / 1e-14` relatively; such a row stays only when the others do not reproduce the dependent one within twice `TAU` (2-norm) without it, tried first through a fresh factor of the others in the solve's column order, which fills no more than the solve's, and then by least squares. Only a settled fit, whose last correction moves the combination by under a hundredth of `TAU`, shows that they cannot; otherwise the removal is undecided and the diagnosis `unavailable`. Every witness must also reproduce its row within twice `TAU`. An insertion's remainder shrinks with the earlier pivots, so rows with small pivots can make a row look dependent relative to coefficients near 1e6 while their combination misses it by 5e-5. Its residuals then change as the sketch moves and cannot tell redundant from conflicting, so the diagnosis is `unavailable` rather than blaming a relation. A witness agrees when the same combination of residuals is within the rows' acceptance tolerances. Rank is unclear when the independent rows are not shown to have a smallest singular value of at least `1e-7`. Before 0.0.751 that made the diagnosis `unavailable`. From 0.0.751 (wire protocol 4) a row whose insertion or witness cannot be decided is left out of the factor and later rows are decided as before. A converged group with unclear rank is then `uncertain`: its witnesses are labelled, freedom is unknown, it skips the move toward the nearest solution and its values are not rounded to short decimals. The application solves it with freedom unknown, as near a tangency, where PlaneGCS also solves. Before 0.0.752 that value was estimated by four inverse iterations over the factor's pivot columns. An estimate approaches from above, so it could call rank clear beside a weak direction, and leaving out the columns without pivots made it falsely unclear for a nearly straight arm, whose second link leaves a tiny lead in the joint's columns. From 0.0.752 no estimate decides. Leaving out columns can only lower the rows' smallest singular value, so a lower bound over the pivot columns, the triangle `T`, that reaches `1e-7` shows rank clear. The first bound costs two passes over `T`: with `C` its comparison matrix (`|T_ii|` on the diagonal, `-|T_ij|` off it), `|T^-1| <= C^-1` entrywise, so `1 / sqrt(max(C^-1 1) max(C^-T 1))` bounds it, with slack for rounding; these sums never cancel. It is far too low when entries of `T^-1` cancel, as along a chain whose links alternate in sign. The second is `1 / ||T^-1||_F`, at most `sqrt(rank)` times below the true value, from one sparse triangular solve per pivot that visits only the pivots it reaches; a chain makes it cost the square of its length. Otherwise the singular values of the independent rows themselves are computed: those of `S` in `R^T = Q S`, factored by the rotations of the witness fit within the group's fill limit, and taken densely (Householder triangle, then Jacobi on the symmetric embedding, accurate to about `epsilon` absolutely) for at most 32 rows. Rank is clear when the smallest reaches `1e-7`; more rows or a fuller factor leave it unclear. The dense step costs up to about 41 million counted entries for 30 rows. These checks past the linear bound only decide whether rank is clear, so together they take at most 64 million counted entries, 20 million of them for the inverse's rows, and half the work left, leaving the rest to the solve and the diagnosis; past that rank is unclear rather than the diagnosis unavailable, and before the first solve no rows are set aside. The check of rows dependent at the start uses the same rule within the group's fill limit, and only when some rows would be set aside. In native release builds, solving 3,200 chained midpoints, staircases of 200 to 2,000 steps and 5,000 links took as long as before; the inverse's rows alone took 35 ms instead of 7.5 ms for the midpoints, and 10,000 links ran out of work.
  - **Labels.** Each witness sets aside one equation: one of the constraint with fewer equations, then of the later constraint, then the earlier equation. Witnesses of one constraint can lie in different groups, as with the two axes of a coincidence, so this runs across all groups. An equation set aside whose witnesses all agree is redundant; every constraint of a witness without a redundant equation conflicts. TypeScript maps the label bits to source ids, including partial redundancy. From 0.0.756 a relation compiled to constraints labelled apart, as a fixed point's two axes, is only conflicting when any of them conflicts, not also redundant through another; the seeded fuzz found fixed points named both, which PlaneGCS never does in the corpus. Degrees of freedom are the unknowns less the rank, reported only without conflicts.
  - **Stalled conflicts.** The nearest point of a conflicting sketch often collapses geometry, as a triangle too long for its sides flattens. Gauss-Newton approaches it only linearly and stops about `sqrt(epsilon)` short relatively, where rank at `TAU` is unclear. A group that did not converge and whose rank is unclear is diagnosed again with dependence at `1e-6` (`STALLED`), with the singular value gate unchanged. Such a diagnosis is `suspected`: it reports conflicts only, with no freedom. A row near a conflict without being in it can be blamed too, and a satisfiable sketch stuck at a stationary point is blamed as conflicting. The application message for it is "could not be met together from this start". From 0.0.754 (wire protocol 5) such a group, unless it is a drag, is blamed for relations that are the same function of the same values, up to their value and sign: one kind over the same operands, or a distance or a difference between the same two values either way round, as repeated dimensions are. Those depend on each other at every point and their residuals combine to the same constant, so a pair held at values further apart than both rows' tolerances at the start is a conflict wherever the sketch moves, and a pair that agrees is a repetition. Angles are left out: their residuals wrap by a turn, so two angles a hair either side of 60 degrees, starting 180 degrees from both, combine to nearly a turn there and to nothing where they hold. When some pair disagrees, the group is blamed for its repeats: `from-start`, with their conflicts and redundancies but no freedom, and the values where the solve stopped. Otherwise it is diagnosed at `STALLED` as above. On `overlapping-conflicts`, distances of 10, 12 and 14 and a vertical offset of 20 between two points, the three distances repeat each other, so native names the same three as PlaneGCS; the impossible triangle has no repeats and stays suspected. In 0.0.754 the repeats were read from a diagnosis at the start values, and only for a stall that diagnosed as suspected. From 0.0.756 they are read from the relations alone, before any rank, which also blames them where the stall runs off and cannot be diagnosed at all: the seeded fuzz found four such sketches, a coordinate held at two values or a horizontal line given a vertical offset beside relations whose stall ran off, that were unavailable and are now kept as fixtures. Kinds whose residual ignores the value they carry, as a point on a line, are held at zero whatever it is, so two copies of one never disagree. Other dependencies a start shows can be accidents of where it begins: a point that must be 5 from two centres 8 apart, starting on the line between them and held there by symmetry, stops at (4, 0) with both distances dependent there too, though (4, 3) meets them, so only repeats are blamed. Finding them costs a sort of the group's equations, within the group's work; past it the group is diagnosed at `STALLED`. When groups are diagnosed differently the sketch takes the most severe kind, in the order diagnosed, uncertain, incomplete, from-start, suspected, nothing free, unavailable.
  - **Incomplete.** From 0.0.754 a converged group whose diagnosis runs out of work, or that was accepted without a factor to diagnose because its solve ran out of work or was too large to factor after acceptance, is `incomplete`: it labels nothing and leaves freedom unknown, while the other groups are still diagnosed and labelled.   - **Copies of undecided rows.** From 0.0.754 a row that exactly copies a row left out as undecided, or its negation, depends on that row alone and is labelled as its residuals agree, so a repeated relation beside a near tangency is still found. Matching reads at most the rows' own size and is not charged to the work limit, so it never changes what else is decided.

      - It runs out of the group's work, which it spends on its steps before it diagnoses. It then ends too large, or converged with its diagnosis incomplete and its freedom unknown. With the default limits, 28,250 unknowns held by differences to one pinned at 0, all starting at 10, end too large after 6 iterations. 28,275 starting at 1e-10 converge with their diagnosis incomplete. Through classes, both are pinned without a step and diagnosed with no freedom left.

- From 0.0.776 the module speaks protocol 6. An options word can ask which parameters the lasting equations determine and which they leave free (`define` in `src/diagnose.rs`), and the reply ends with a definition code for each parameter. Only constraint inspection asks; commits, previews and drags do not, and a drag cannot.
  - Each probe rotates a parameter's unit row into the diagnosis factor and restores it. The probes take their work from an allowance of 20,000,000 entries for the whole solve, apart from the solve's own work, so a solve that asks is answered as one that does not, bit for bit. The Rust tests check that for each sketch they solve through the wire.
  - A probe only proposes an answer. Each answer is then certified against the group's rows themselves, because the factor can hide motion in two ways. It leaves out leads within the dependence distance: a lead of 5e-11 left out hid a free direction that moves another point by about 5e-6. Its rounding can also hide motion: two equal lengths from nearly the same anchors showed a point moved by 9.6e-11 per unit of their free direction, which in fact moves it by 4.4e-10.
    - **Determined** means the certified projection of the parameter's unit vector onto the directions the independent rows leave free is at most `TAU` (1e-10). That projection is at most what any combination of the rows misses of the unit vector. The factor proposes the combination by seminormal equations, in up to 8 passes while the miss shrinks, with the coefficients kept in twice the working precision. The miss is summed per column with error-free products and sums (Dot2, Ogita, Rump and Oishi, 2005), and its bound includes that sum's own rounding. `TAU` is the dependence distance, so a parameter is determined just when fixing it would add only a dependent equation.
    - **Free** means a direction from the factor is certified to move every row by at most `TAU` per unit, the rank tolerance. It must also move the parameter by more than `CERTAIN` (1e-7) per unit, plus the most the nearest exact free direction can differ from it. That difference is what the direction moves the rows, divided by a bound from below on the rows' smallest singular value. The bound is the certainty margin less what the factor left out, and is used only when that is under half the margin. The rows' and the direction's own rounding is bounded the same way.
    - A parameter between the two thresholds, one with no certificate, and one past the allowance are not analysed. A group of full rank has no free direction and is all determined without a probe, which rests on rank being certain at `CERTAIN`. The factor's own rounding moves its smallest singular value by about `epsilon` times the rows' norm, as it does for rank.
    - Seeded tests check every analysed code against exact references. One set is 20,000 random groups with entries near the dependence distance. The other is 20,000 pairs of nearly parallel rows, where one column differs by 3e-7 to 1e-5 and the others by a few ulps, so that the free direction moves a column by between `TAU` and `CERTAIN`.

## Sketch-solver workloads, step 2c

Run `npm run cad:benchmark -- --group solver-workloads`. It measures the application's production runtime, `createCadSketchNativeRuntime`, as one solver, `native`. From 0.0.750 to 0.0.756 it measured three modes: `planegcs` (PlaneGCS alone), `native-only` (native with no fallback) and `native-first` (what the app ran). Sections are `workloads`, `edits`, `drag`, `sweep`, `cold`, `memory` and `capacity`; choose them with `--sections` and fixtures with `--cases <ids>`. Each section, and each workload fixture, is written as its own JSON part to `--out` (default `tmp/cad-benchmark/solver-workloads-<version>-<commit>`, with `-quick` for `--quick`), each written to a temporary file and renamed into place. The directory's `manifest.json` records the run's identity: the commit, a sha256 of uncommitted changes to tracked files and untracked files under `src`, `scripts` and `packages`, the module's sha256, the host (CPU, cores, memory, platform, Node and V8 versions, Node flags and `NODE_OPTIONS`) and the settings (`--runs`, `--quick`). Each part records the same identity; the memory part also records the fixtures it measured, and resuming with other `--cases` is refused for it. A burst into a directory with another identity is refused; parts already there with the same identity are kept, so a run can be stopped and resumed in short bursts on an idle host, and an unreadable part is measured again. `--aggregate <directory>` joins the parts into `report.json` and `summary.md` with the run's identity, and refuses unreadable parts or parts with another identity. Seven latency samples and trajectories are the default; `--quick` uses three and 100 repeated solves instead of 1000; `--runs N` changes samples, trajectories and cold processes. Capacity always uses three samples per size and searches at most 4096 connected rectangles. Reports include Node version, CPU, all calibration brackets, outcomes, how native answered (`native:answer`, or the reason it is not certain), source diagnostics, stage statistics, resource observations and correctness failures.

### Timing and comparison rules

The solver implements the existing `CadSketchSolver` interface. Every timer encloses its public `solve(input)`, including boundary parsing, compilation, solving, mapping, the fixed-value check, building the solved graph from the accepted request with `cadSketchGraphWithSolvedValues` (0.0.745) and the same `checkCadSketchGraph` acceptance. The benchmark's own `cadSketchSolutionMatchesInput` correctness check runs outside timing. The solver is `createCadSketchNativeRuntime` itself, with its attempt judging, kept groups, diagnosis and instance replacement. The runtime reports its stage timings through an observer that reads no clock when none is attached. None of this changes how the application solves.

From 0.0.742 native rows are the **full job**: native maps its diagnosis to source ids and rejects in the order the PlaneGCS runtime did, conflicting first, then redundant or partially redundant, then a convergence failure. An unavailable diagnosis is a failure, never a clean result. A suspected diagnosis, a stall short of a collapsed point, blames no relation and is rejected as a failure without conflict ids or freedom; until 0.0.757 `native-first` asked PlaneGCS for it. `cadSolverWorkloadBenchmark.test.ts` compares every fixture with PlaneGCS's answer in the frozen corpus, which holds every workload input, trajectory frame and sweep drag; four differences are reviewed: `tangency-near` solves natively where PlaneGCS failed the graph check, `impossible-triangle` is a rejection native cannot attribute, `fully-fixed-conflict` names the unmet relation, and from 0.0.754 `overlapping-conflicts-repeated` names a repeated 10 redundant, where PlaneGCS, whose sketch still failed without the relations it set aside, named it conflicting. Every answer records how native answered and why it is not certain, so rows show the share of each reason. Runs recorded before 0.0.742 measured native solving without diagnosis, runs before 0.0.750 measured a native adapter apart from the runtime, without drags, and runs before 0.0.757 could fall back to PlaneGCS; none is comparable with these.

Each workload has an untimed warmup, followed by repetitions in a CPU calibration bracket. Fixtures, edits, cloning, correctness checks and statistics are outside timing. Each workload starts with a fresh WASM instance; initialization is outside warm timings. Before 0.0.757, reusing one PlaneGCS instance across many unrelated workloads caused heap exhaustion before the 88-rectangle chain in an initial probe, so the suite avoids carrying allocation history between workloads; repeated-instance memory gets its own measurement.

Each fixture measures the first solve and a re-solve of its own accepted graph. Re-solving an already-solved graph approximates diagnosis cost but still includes parse/compile, convergence detection, mapping and validation. It is not an isolated diagnosis timer. Rejected first solves have no already-solved input, so their re-solve rows are skipped. Two edit sequences start from the die's accepted graph: slot radius 3 to 3.5 mm, then to 4.2 mm, and adding then removing one released die dimension. Every accepted result feeds the next edit. Failed edits never become the next input.

Drag trajectories run from the start (each frame from the trajectory's first accepted graph, as editor previews do) and chained (each accepted frame feeds the next). `die-slot` releases only the slot radius of the connected die, then moves its upper-left endpoint through 60 frames with a reversal; frame 45 targets an unreachable x coordinate, which is projected onto the remaining freedom. `arm` stretches a two-link arm out of reach and back over 47 frames, `four-bar` drags a four-bar linkage out of reach over 10 frames, and `tangency` approaches a tangency to 7.5e-6 mm and lands on it. Each group records outcomes, native drag outcomes (reached, projected, limited or stalled), how native answered, the largest distance to a target, every frame's target and error, frame p50/p95/p99 and raw counts over 8 ms. Percentiles use `cadBenchmarkStats` nearest ranks. Frames are measured back-to-back without frame pacing or a rendering budget. The `sweep` section drags every point of the die and of the free die that the solver may move (both coordinates numeric, not pattern-generated or referenced) by a small, a large and an out-of-reach offset. Until 0.0.757 it counted drags that ended further from their targets than the first mode's; the test now holds each drag to PlaneGCS's frozen answer plus 1e-6 mm.

`totalMs` is the public-call total. `stagesMs` partitions it into `parseCompile` (including component preparation), `nativeCall` (wrapper/buffer work, the native solve and its diagnosis), `mapping` (diagnostic source ids and geometry), and `validation`. Observer and promise overhead remain in totals; stage medians need not sum to the total median. The suite checks every accepted graph again outside timing and detects input mutation. Zero correctness failures means those geometry/integrity checks passed; diagnosis agreement is checked by the tests above.

Use the existing 1.5-times calibration drift rule. Each workload/edit sequence and drag trajectory group records before/after calibration; capacity pairs also have brackets. The cold section brackets all its processes once and is marked `THROTTLED` like any group. A `THROTTLED` group is unsuitable for a latency comparison even if its geometry is correct. Cross-group comparisons also need similar calibration, and cross-host comparisons remain invalid.

### Resource measurements and limits

- Cold probes run in a separate Node process each, with the parent's Node flags, to avoid V8 WASM compilation-cache reuse. The module breakdown records local file read, explicit `WebAssembly.compile`, instantiation/glue and their sum, plus raw/gzip WASM bytes. The first-answer probe times loading through the first answer on the die. Until 0.0.757 it had four scenarios: PlaneGCS alone, native only and native first on the die, and native first on `overlapping-conflicts`, where it also loaded PlaneGCS. The input is built before the timer. OS disk caches are not flushed. Browser/network fetch time, download caching and browser cold startup are unavailable here; a local file read is not a network benchmark.
- Each workload's memory probe uses a fresh instance and records `WebAssembly.Memory.buffer.byteLength` before and after the solve. This is retained linear-memory capacity, a high-water allocation, not live allocator usage. It remains useful when C++ or Rust allocations are freed. Node RSS, JS heap, external-memory and ArrayBuffer deltas are sampled at the call boundaries. GC is uncontrolled and deltas can be negative; they are not attributable peaks. Temporary process-allocation peaks are unavailable while the synchronous WASM call runs.
- The repeat probes seed an accepted die and re-solve it 1000 times in the same instance, then run the die-slot frames from the start 1000 times in another. Memory is recorded after 1, 10, 100 and 1000 calls, with native instance resets. Independent checks happen outside solving, so process deltas also include checker allocations. This does not measure a succession of different large workloads.
- Capacity uses connected rectangle chains, three public solves per candidate in fresh initialized instances, and the median total below 1000 ms. It brackets then binary-searches the integer boundary, up to 4096 rectangles. The report retains every acceptance, rejection, calibration and sample. A result at the search cap is a lower bound; since 0.0.756 native solves 4096 connected rectangles in about 300 ms, so this search reports only that bound, and `scripts/benchmark-cad-native-too-large.ts` finds the size native refuses. A boundary is throttled when the calibrations of its two probes, taken together, differ by more than 1.5 times; it is flagged in the limit and console summary, alongside the largest unthrottled solved probe. Timing noise near one second can move the measured boundary; it is not a product limit. Native capacity includes diagnosis from 0.0.742. Until 0.0.757 PlaneGCS received the same candidates, and its 500,000 parameter/equation product guard refused 89 rectangles.
