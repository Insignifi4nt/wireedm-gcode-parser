# CAD performance baseline

`npm run cad:benchmark` measures the CAD kernel and sketch solver on fixed workloads and writes JSON reports to `tmp/cad-benchmark/`. Add `-- --quick` for a shorter run or `-- --runs N` to change the sample count (a positive whole number, default 7). `-- --group legacy` selects the original kernel, solver-scaling and drag-preview groups; `-- --group solver-workloads` selects the public-boundary PlaneGCS/native comparison below. The default, `-- --group all`, runs both. No browser or dev server is needed. Use it before and after a change that claims a speed or memory improvement, and record both reports in the pull request.

## Workloads and correctness

`src/features/cad/benchmark/cadBenchmarkCases.ts` defines the workloads. Kernel cases are complete documents with edit steps and analytic expected volumes. `cadBenchmarkCases.test.ts` builds every step in the normal Vitest suite, so a case that stops producing its analytic geometry fails CI instead of producing misleading timings. The script also marks such a step `INCORRECT` and exits non-zero.

| Case | What it isolates |
| --- | --- |
| `plate-hole-pattern` | Ordinary sketch, extrude, linear pattern and boolean cut; the width edit invalidates every feature. |
| `gear-and-plate` | A gear plugin profile (hundreds of faces) beside an independent holed plate. The plate edit rebuilds the unchanged gear. `affectedBodies` is the plate alone, with its unchanged hole pattern, and has its own analytic volume. |
| `box-fillet-all-edges` | Rolling-ball fillet of all twelve box edges and a radius edit. |

Solver workloads are independent, fully constrained rectangles (4 lines and 7 relations each). The connected capacity workload instead places each rectangle by two axis distances from the previous one, so all rectangles form one solver group. The drag preview uses documents with 1, 4 and 8 independent graph sketches of 10 rectangles. The first rectangle of the first sketch has its fixed corner released, and one corner move is prepared through `prepareCadEdits`, as a sketch drag preview does. The suite checks that the rectangle follows the drag and that every other sketch is unchanged. A dependent workload adds a second sketch that uses the first rectangle's bottom edge. It drags the referenced rectangle, which must re-solve the dependent, and a second released rectangle, which must not.

## Metrics

- `buildMs`: uncached `buildCadKernelModel` of the full document. `coldMs` is the first build of the first step in a fresh module.
- `shippedEditMs`: the previous step followed by this step through `createCadKernelRuntime`, which caches only a whole document.
- `affectedBodiesMs`: uncached build of only the bodies the edit changes, including unchanged inputs they need. It is sampled alternately with `shippedEditMs` so both see the same clock speed. A rebuild that reuses unaffected bodies should take no longer than this; it can be faster by also reusing unchanged inputs.
- `payload`: triangles, plain-array numbers and JSON size of the build result that crosses the worker boundary.
- `mainThread`: `structuredClone` of the reply, `isCadKernelReply` validation and `prepareCadMeshDisplay` for every mesh. The app pays these on the main thread for each build.
- `memoryBytesAfterRebuilds`: OpenCascade linear-memory capacity after 1, 10 and 50 edits through one shipped runtime, alternating the case steps so each edit replaces the cached model. WASM memory grows but never shrinks, so this is a high-water mark. Each case runs in a fresh OpenCascade module, so its numbers do not depend on the cases before it.
- Solver `scaling`, `drag`, `dragPreview` and `capacity`. Each drag preview reports `solvesPerPreview` (solver calls for one preview), `prepareMs` for the whole preparation and `solverCallMs` for the solver calls inside it (constraint compilation, the native solve and reply validation); the difference is document parsing, reference refresh and checks. PlaneGCS has fixed linear memory and aborts with OOM, so capacity uses a fresh module per size. It probes independent and connected rectangles separately, records each size's native parameters and constraints, and reports the largest rectangle count that solved and the first that did not, with its rejection reason.
- From 0.0.750 `nativeFirst` repeats `scaling` and `dragPreview` through the native-first runtime the app uses, beside the PlaneGCS rows.
- `cpuCalibrationMs`: a fixed JavaScript loop timed before and after each measurement group: full builds, edits and main-thread work for each kernel step, and each solver size, the solver drag and each drag-preview size. Laptops reduce clock speed under sustained load; the development host below ran the same loop 3.5 times slower after about three seconds. The script marks a group `THROTTLED` when its calibrations differ by more than 1.5 times and warns when they do across the run. Use only unthrottled groups, compare groups with similar calibration, and never compare across hosts.

## Findings that set the order of work

1. Drag previews re-solve every graph sketch in the document, so preview cost grows with unrelated sketches.
2. PlaneGCS aborts on a few hundred constrained entities because its memory cannot grow; the worker reports the raw abort text and restarts. Measured with one solver group, the abort depends on unfixed parameters times constraints: 760 x 760 solved and 800 x 800 aborted for independent rectangles, while a connected chain solved 800 x 800 and aborted at 1000 x 1000.
3. Every edit rebuilds every feature. Unchanged expensive bodies dominate edits of cheap ones. OpenCascade memory already grows from 100 to 127 MiB between the 10th and 50th edit of the holed plate, so a feature cache must show no more growth than that over the same 50 edits.
4. Build results cross the worker as plain arrays (1.1 MiB JSON for 5.8k triangles) and are validated and prepared for display again on the main thread. That costs about 5 ms a build here, so it is a payload and memory cleanup, not the main latency.

Proposed order: solve only edited sketches and their reference dependents, then solve independent sketch components separately with a clear limit message; incremental feature rebuilds keyed by a chain hash with bounded memory after 50 rebuilds as a gate; typed-array transfer with display preparation in the worker. Rust or kernel replacements are considered only where this benchmark shows the remaining time is inside the native kernel or solver.

## Native sketch solver (in progress)

`packages/sketch-solver` is our own Rust constraint solver, compiled to a 92 kB WebAssembly module (33 kB gzip) with no dependencies. From 0.0.739 it is built, tested and compared with PlaneGCS, but the app does not load it yet.

- `compileCadSketchEquations` turns a sketch into scalar parameters and twelve kinds of scalar equation, and the module solves them.
  - Each connected group of unknowns gets its own damped Gauss-Newton solve, with exact gradients from dual numbers.
  - Each equation is divided by its gradient norm over the unknowns, so every residual reads as the distance they must move.
  - Each step comes from a Givens QR of the weighted Jacobian, not the normal equations, so roundoff does not move the free directions of an under-constrained sketch.
  - From 0.0.740 the QR is sparse:
    - Rows keep their authoring order. Columns take a minimum-degree order fixed by the structure, so a chain of profiles fills like a band.
    - Each damping trial refactors from `sqrt(mu) I` and then rotates in the Jacobian rows. A row meeting a diagonal-only row carries on with only its own entries, so most rows stop near their own length. Rotating the damping in after the Jacobian, as MINPACK does, would run each damping row down the whole elimination tree: about 300 million updates per trial for a 5,000-link chain.
    - In that order, the motion along directions the Jacobian leaves free depends on roundoff whenever dependent rows disagree within a step. Conflicting relations always do. Redundant ones also do before the solve converges, when their linearizations are different functions of the same motion: an angle of 90° plus a perpendicular relation on the same lines, far from the origin, moves a free midpoint by about 0.4 µm. The same relation entered twice does not, because its rows agree exactly. Both kinds of sketch are rejected by diagnosis. From 0.0.742 rows dependent at the start stay out of the first solve, which removes this drift (see below).
    - For sketch-like structure, where profiles join in chains and trees and shared parameters such as a radius are eliminated last, time and memory grow about linearly with the size of a group. A group whose columns are all coupled at random fills almost completely, as in a dense factorization.
  - Native code cannot be interrupted, so each group has limits:
    - The ordering gives the exact fill of the factor before any numeric work. A group above 2,000,000 entries (about 32 MiB) is left in place. The ordering stops as soon as the fill so far, plus the edges still present and the diagonals still to come, passes that limit, so its own memory stays within about twice the limit.
    - The ordering, and every rotation after it, count the entries they write against 400,000,000. Rotations check the count before every step, so a group stops within one step of the limit, where it got to. From 0.0.742 a group's diagnoses continue from the count its solve reached, and a diagnosis that runs out is `unavailable`. Labelling across groups has its own allowance of the same size.
    - In a native probe, random groups of 2,000 to 4,200 unknowns whose factors would be dense are refused in under half a second.
    - Either reports `too-large`. This replaces the PlaneGCS limit of 500,000 unfixed parameters times equations, which a chain of 89 rectangles already exceeds.
  - Convergence is judged apart from that weighting:
    - each residual must be within the driver tolerance in millimetres;
    - each direction error must be within 1e-12 radians, or the roundoff of its coordinates at the far end of the longer line.
  - The solver status only reports convergence of its own equations. As with PlaneGCS, the graph checks decide whether a result is accepted, including degenerate lines, angle sectors and the distance between collinear segments.
  - Iteration continues to roundoff, because the graph checks require coincident points to agree within 8 ulp of their coordinates.
  - From 0.0.743 polishing past acceptance stops at the second step in a row that gains less than a quarter of its prediction and less than `1024 epsilon` of the cost. Such a step moves only roundoff: a direction whose roundoff floor sits above the polish level, as in the die after its slot radius grows 0.5 mm, otherwise kept the loop taking them until they vanished, 50 iterations instead of 6. Both conditions are needed. Leaning guides that converge linearly gain what they predict, and a point near a tangency can gain 8% of the cost with a ratio of 0.08. One such step can still be real, as when a point drags its own guide, so a single one does not stop polishing.
- From 0.0.749 a group that converged with freedom left, diagnosed without conflicts or redundancies, moves on toward the solution nearest its start values. Damped Newton steps reach a solution but not the nearest one where relations bend: a direction residual is a normalized sine, so its step moves a point across its line rather than straight onto the line it must lie on. Applying Parallel between a free point's line and a horizontal reference moved the point from (35, 15) to (35.714, 20) instead of (35, 20). Each of at most four rounds, sharing the 100-iteration allowance, solves the linearized relations for the least change from the start, `min |z|` with `J z = J (x - start) - r`, converges again from `start + z` and stands only when every row is still accepted and the group ended nearer its start. That reaches the nearest solution when the relations are linear in the moved unknowns and only brings the group nearer otherwise. The moved group is diagnosed again, and unless its rank and its lack of witnesses are unchanged the first diagnosed solution is kept: a point held 1 mm from two points 2 mm apart lies on a tangency, and a nearer solution there read as rank-unclear. Reported iterations include the correction. Well-constrained groups, such as the die, and drags skip it; a group with freedom left pays about one factorization more, and a second diagnosis when it moved. A group whose rank is too close to call skips it too. Measured for 0.0.754 over the 1,539 native solves of the full Vitest suite, the only such solves that were not drags were nine in the tangency lifecycle, a point held by a circle and a line at their tangency with nothing free and so nothing to move; the rule stays until a sketch shows otherwise.
- From 0.0.742 the module diagnoses every solve, as PlaneGCS does (`src/diagnose.rs`, wire protocol 2):
  - Each equation carries the tag of its source constraint (coincident, midpoint and symmetric relations have two equations) and a temporary flag for drag targets, which are solved but not diagnosed.
  - **Rows dependent at the start.** Before each group is solved, its lasting rows go into a rank-only factor at the input values. Rows within `TAU = 1e-10` of the span of earlier ones (once each row has unit norm) stay out of a first solve. That result stands if every row is then accepted. Otherwise the group is restored and solved with every row, sharing the 100 iterations and the work limit. Unclear rank or an exhausted budget solves every row.
  - **Diagnosis at the result.** Rows go in authoring order into an undamped sparse factor in the solve's column order. A dependent row gets a witness: the earlier rows that reproduce it. Its coefficients come first through the same factor, by seminormal equations corrected from what the combination still misses until the correction stops shrinking it; this stays as sparse as the solve. The factor's pivot columns can be far worse conditioned than the rows themselves, so a combination found this way that reproduces the row is a witness, but one that does not proves nothing. The rows it chose are then fitted on their own by least squares: their transpose is factored by rotations and corrected the same way. A value shared by many rows makes that factor dense, so it is held to the group's fill limit, and a fit that would pass it leaves the diagnosis `unavailable`; 3,200 midpoints around one free value are diagnosed through the solve's factor in about 2 MiB. Coefficients and misses are kept in twice the working precision (error-free sums and products), so a combination found within the distance is, and terms near 1e6 that cancel neither hide a real miss of 1e-9 nor make one up. A row within `TAU` of the span can lean on a nearly parallel one by up to about `epsilon / 1e-14` relatively; such a row stays only when the others do not reproduce the dependent one within twice `TAU` (2-norm) without it, tried first through a fresh factor of the others in the solve's column order, which fills no more than the solve's, and then by least squares. Only a settled fit, whose last correction moves the combination by under a hundredth of `TAU`, shows that they cannot; otherwise the removal is undecided and the diagnosis `unavailable`. Every witness must also reproduce its row within twice `TAU`. An insertion's remainder shrinks with the earlier pivots, so rows with small pivots can make a row look dependent relative to coefficients near 1e6 while their combination misses it by 5e-5. Its residuals then change as the sketch moves and cannot tell redundant from conflicting, so the diagnosis is `unavailable` rather than blaming a relation. A witness agrees when the same combination of residuals is within the rows' acceptance tolerances. Rank is unclear when the independent rows are not shown to have a smallest singular value of at least `1e-7`. Before 0.0.751 that made the diagnosis `unavailable`. From 0.0.751 (wire protocol 4) a row whose insertion or witness cannot be decided is left out of the factor and later rows are decided as before. A converged group with unclear rank is then `uncertain`: its witnesses are labelled, freedom is unknown, it skips the move toward the nearest solution and its values are not rounded to short decimals. The application solves it with freedom unknown, as near a tangency, where PlaneGCS also solves. Before 0.0.752 that value was estimated by four inverse iterations over the factor's pivot columns. An estimate approaches from above, so it could call rank clear beside a weak direction, and leaving out the columns without pivots made it falsely unclear for a nearly straight arm, whose second link leaves a tiny lead in the joint's columns. From 0.0.752 no estimate decides. Leaving out columns can only lower the rows' smallest singular value, so a lower bound over the pivot columns, the triangle `T`, that reaches `1e-7` shows rank clear. The first bound costs two passes over `T`: with `C` its comparison matrix (`|T_ii|` on the diagonal, `-|T_ij|` off it), `|T^-1| <= C^-1` entrywise, so `1 / sqrt(max(C^-1 1) max(C^-T 1))` bounds it, with slack for rounding; these sums never cancel. It is far too low when entries of `T^-1` cancel, as along a chain whose links alternate in sign. The second is `1 / ||T^-1||_F`, at most `sqrt(rank)` times below the true value, from one sparse triangular solve per pivot that visits only the pivots it reaches; a chain makes it cost the square of its length. Otherwise the singular values of the independent rows themselves are computed: those of `S` in `R^T = Q S`, factored by the rotations of the witness fit within the group's fill limit, and taken densely (Householder triangle, then Jacobi on the symmetric embedding, accurate to about `epsilon` absolutely) for at most 32 rows. Rank is clear when the smallest reaches `1e-7`; more rows or a fuller factor leave it unclear. The dense step costs up to about 41 million counted entries for 30 rows. These checks past the linear bound only decide whether rank is clear, so together they take at most 64 million counted entries, 20 million of them for the inverse's rows, and half the work left, leaving the rest to the solve and the diagnosis; past that rank is unclear rather than the diagnosis unavailable, and before the first solve no rows are set aside. The check of rows dependent at the start uses the same rule within the group's fill limit, and only when some rows would be set aside. In native release builds, solving 3,200 chained midpoints, staircases of 200 to 2,000 steps and 5,000 links took as long as before; the inverse's rows alone took 35 ms instead of 7.5 ms for the midpoints, and 10,000 links ran out of work.
  - **Labels.** Each witness sets aside one equation: one of the constraint with fewer equations, then of the later constraint, then the earlier equation. Witnesses of one constraint can lie in different groups, as with the two axes of a coincidence, so this runs across all groups. An equation set aside whose witnesses all agree is redundant; every constraint of a witness without a redundant equation conflicts. TypeScript maps the label bits to source ids, including partial redundancy. Degrees of freedom are the unknowns less the rank, reported only without conflicts.
  - **Stalled conflicts.** The nearest point of a conflicting sketch often collapses geometry, as a triangle too long for its sides flattens. Gauss-Newton approaches it only linearly and stops about `sqrt(epsilon)` short relatively, where rank at `TAU` is unclear. A group that did not converge and whose rank is unclear is diagnosed again with dependence at `1e-6` (`STALLED`), with the singular value gate unchanged. Such a diagnosis is `suspected`: it reports conflicts only, with no freedom. A row near a conflict without being in it can be blamed too, and a satisfiable sketch stuck at a stationary point is blamed as conflicting. The application message for it is "could not be met together from this start". From 0.0.754 (wire protocol 5) such a group, unless it is a drag, is blamed for relations that are the same function of the same values, up to their value and sign: one kind over the same operands, or a distance or a difference between the same two values either way round, as repeated dimensions are. Those depend on each other at every point and their residuals combine to the same constant, so a pair held at values further apart than both rows' tolerances at the start is a conflict wherever the sketch moves, and a pair that agrees is a repetition. Angles are left out: their residuals wrap by a turn, so two angles a hair either side of 60 degrees, starting 180 degrees from both, combine to nearly a turn there and to nothing where they hold. When some pair disagrees, the group is blamed for its repeats: `from-start`, with their conflicts and redundancies but no freedom, and the values where the solve stopped. Otherwise it is diagnosed at `STALLED` as above. On `overlapping-conflicts`, distances of 10, 12 and 14 and a vertical offset of 20 between two points, the three distances repeat each other, so native names the same three as PlaneGCS; the impossible triangle has no repeats and stays suspected. In 0.0.754 the repeats were read from a diagnosis at the start values, and only for a stall that diagnosed as suspected. From 0.0.756 they are read from the relations alone, before any rank, which also blames them where the stall runs off and cannot be diagnosed at all: the seeded fuzz found four such sketches, a coordinate held at two values or a horizontal line given a vertical offset beside relations whose stall ran off, that were unavailable and are now kept as fixtures. Other dependencies a start shows can be accidents of where it begins: a point that must be 5 from two centres 8 apart, starting on the line between them and held there by symmetry, stops at (4, 0) with both distances dependent there too, though (4, 3) meets them, so only repeats are blamed. Finding them costs a sort of the group's equations, within the group's work; past it the group is diagnosed at `STALLED`. When groups are diagnosed differently the sketch takes the most severe kind, in the order diagnosed, uncertain, incomplete, from-start, suspected, nothing free, unavailable.
  - **Incomplete.** From 0.0.754 a converged group whose diagnosis runs out of work, or that was accepted without a factor to diagnose because its solve ran out of work or was too large to factor after acceptance, is `incomplete`: it labels nothing and leaves freedom unknown, while the other groups are still diagnosed and labelled. Before, the whole sketch was `unavailable` and lost every label. A group that did not converge and runs out of work, and labelling that runs out, are still `unavailable`.
  - **Copies of undecided rows.** From 0.0.754 a row that exactly copies a row left out as undecided, or its negation, depends on that row alone and is labelled as its residuals agree, so a repeated relation beside a near tangency is still found. Matching reads at most the rows' own size and is not charged to the work limit, so it never changes what else is decided.
  - **Nothing free.** With no unknowns, relations that are not met conflict and met ones are left unlabelled.
  - Large conflicting groups can still stop at the iteration limit far from their collapsed nearest point. They are then diagnosed there, usually with no ids, as PlaneGCS does at its start; an 11-point chain is diagnosed and a 31-point one is not.
  - Compared with PlaneGCS on every solve in the differential suites (409 diagnosed), 394 results are identical in freedom and conflicting, redundant and partially redundant ids. Four are reviewed differences: three where PlaneGCS's unnormalized perpendicular and parallel gradients also blame a line's length, and one where PlaneGCS sets aside the earlier of two collinear relations because it is in more dependencies. Eleven are relations not met with nothing free, which PlaneGCS reports as success and the graph checks reject; native names them. Hand probes found two more PlaneGCS gaps, a midpoint with two horizontals where PlaneGCS blames only one and a coincidence before a midpoint that PlaneGCS calls conflicting although the sketch is consistent.
- From 0.0.755 the sketch suites solve with native alone. The shared test solver defaults to `native-only` and rejects any solve whose native instance failed to load or trapped, and the setup files then fail that test after it ends, so a test expecting a rejection cannot pass on it; only the fallback tests pick `native-first`, and `cadSketchSolverRuntime.test.ts` keeps what PlaneGCS alone does. The `native-differential` test project compares each solve in those suites with PlaneGCS alone on the same input. Every compiled input must give the same equations. Every solved sketch must also solve natively and pass the graph checks, and well-constrained sketches must match PlaneGCS within 1e-8.
- From 0.0.755 a frozen corpus keeps PlaneGCS's answer to every sketch solve the CAD suites make, so native can still be compared with it after PlaneGCS is removed.
  - `npm run solver:corpus -- --update` runs the CAD suites and records each solve input with the tests that made it. It asks PlaneGCS alone for each input's outcome and checks that native compiles the input to the equations PlaneGCS's compilation restates. `--check` fails when an input the suites now make is missing or has another outcome. Run `--check` on the parent of the PR that removes PlaneGCS.
  - Records are kept by input hash in `src/features/cad/sketch-solver/__tests__/fixtures/planegcs-corpus/`: `records.jsonl`, the graphs in `graphs.json.gz`, and `manifest.json` with the PlaneGCS version and the native module hash they were captured against. Inputs the suites no longer make are kept.
  - `planeGcsCorpus.test.ts` needs no PlaneGCS. It compiles each record, which must give the frozen model hash, and answers it with native alone through the production runtime. Every applicable difference is listed: a rejection of what PlaneGCS solved or a solution of what it refused as invalid, another reason, status (PlaneGCS's converged counts as success), freedom, conflicting, redundant or partially redundant ids, or graph issues by source and code, well-constrained geometry further than 1e-8, or a drag that ends further from its target. Any record with differences fails unless it is reviewed there by hash, and a reviewed record pins its differences and native's answer exactly, so it fails when either changes. A reviewed geometry difference also bounds how far native's solution may be from PlaneGCS's, and a reviewed further drag how far native may end from its target, in mm. Free solutions, and solves native accepts where PlaneGCS rejected the input or found it too large, are only counted.

## Sketch-solver workloads, step 2c

Run `npm run cad:benchmark -- --group solver-workloads`. From 0.0.750 it measures the application's production runtime in three modes: `planegcs` (PlaneGCS alone), `native-only` (native with no fallback, showing its own gaps) and `native-first` (what the app runs). Sections are `workloads`, `edits`, `drag`, `sweep`, `cold`, `memory` and `capacity`; choose them with `--sections`, fixtures with `--cases <ids>` and modes with `--solvers`. Each section, and each workload fixture, is written as its own JSON part to `--out` (default `tmp/cad-benchmark/solver-workloads-<version>-<commit>`, with `-quick` for `--quick`), each written to a temporary file and renamed into place. The directory's `manifest.json` records the run's identity: the commit, a sha256 of uncommitted changes to tracked files and untracked files under `src`, `scripts` and `packages`, both modules' sha256, the host (CPU, cores, memory, platform, Node and V8 versions, Node flags and `NODE_OPTIONS`) and the settings (`--runs`, `--quick`, `--solvers`). Each part records the same identity; the memory part also records the fixtures it measured, and resuming with other `--cases` is refused for it. A burst into a directory with another identity is refused; parts already there with the same identity are kept, so a run can be stopped and resumed in short bursts on an idle host, and an unreadable part is measured again. `--aggregate <directory>` joins the parts into `report.json` and `summary.md` with the run's identity, and refuses unreadable parts or parts with another identity. Correctness failures are kept in their parts, listed first in the summary with the groups that gave them marked `INVALID`, and make both the run and the aggregation exit with a failure. Seven latency samples and trajectories are the default; `--quick` uses three and 100 repeated solves instead of 1000; `--runs N` changes samples, trajectories and cold processes. Capacity always uses three samples per size and searches at most 4096 connected rectangles. Reports include Node version, CPU, sample order, all calibration brackets, outcomes, which solver answered and why native fell back, source diagnostics, stage statistics, resource observations and correctness failures.

`cadSolverWorkloadCases.ts` defines 29 fixtures. `cadSolverWorkloadCases.test.ts` runs each through the native solver alone (PlaneGCS before 0.0.755, whose answers stay in the frozen corpus) and pins the result kind, rejection reason, DOF, status and diagnostic lists in reviewed snapshots. Accepted graphs must preserve source intent and pass independent graph checks. The die's fully constrained result, free variant and shuffled hub also have explicit geometry/intent tests. Do not update snapshots merely to make a changed fixture pass; explain changed acceptance or diagnosis in the review.

### Timing and comparison rules

Every mode implements the existing `CadSketchSolver` interface. Every timer encloses its public `solve(input)`, including boundary parsing, compilation, solving, mapping, the fixed-value check, building the solved graph from the accepted request with `cadSketchGraphWithSolvedValues` (0.0.745) and the same `checkCadSketchGraph` acceptance. The benchmark's own `cadSketchSolutionMatchesInput` correctness check runs outside timing. `planegcs` uses the current PlaneGCS runtime, including connected components, the group-size guard, temporary drag constraints and **always-on diagnosis**. `native-only` and `native-first` are `createCadSketchNativeFirstRuntime` itself, with its attempt judging, kept groups, fallbacks and native instance resets; `native-first` loads PlaneGCS only when it falls back, as the app does. The runtime reports its stage timings through an observer that reads no clock when none is attached. None of this changes the application's solver selection.

From 0.0.742 native rows are the **full job**: native maps its diagnosis to the same source ids and rejects in the same order as the PlaneGCS runtime, conflicting first, then redundant or partially redundant, then a convergence failure. An unavailable diagnosis is a failure, never a clean result. A suspected diagnosis, a stall short of a collapsed point, blames no relation: `native-only` rejects it as a failure without conflict ids or freedom, and `native-first` asks PlaneGCS. `cadSolverWorkloadBenchmark.test.ts` compares every fixture between `planegcs` and `native-only`; four differences are reviewed: `tangency-near` solves natively where PlaneGCS fails the graph check, `impossible-triangle` is a rejection native cannot attribute (`native-first` asks PlaneGCS for it), `fully-fixed-conflict` names the unmet relation, and from 0.0.754 `overlapping-conflicts-repeated` names a repeated 10 redundant, where PlaneGCS, whose sketch still fails without the relations it set aside, names it conflicting. Before 0.0.754 native could not attribute `overlapping-conflicts` either; it now names PlaneGCS's three conflicts, though `native-first` still asks PlaneGCS first. Every answer records which solver gave it and why native fell back, so `native-first` rows show the share PlaneGCS still answers. Runs recorded before 0.0.742 measured native solving without diagnosis, and runs before 0.0.750 measured a native adapter apart from the runtime, without drags; neither is comparable with these.

Each workload has an untimed warmup per mode, followed by repetitions in a CPU calibration bracket. The mode order rotates every repetition, and the starting rotation advances across workloads. Fixtures, edits, cloning, correctness checks and statistics are outside timing. Each workload starts with fresh WASM instances; initialization is outside warm timings. Reusing one PlaneGCS instance across many unrelated workloads caused heap exhaustion before the 88-rectangle chain in an initial probe, even though it solves in a fresh instance. This suite avoids carrying that allocation history between workloads; repeated-instance memory gets its own measurement.

Each fixture measures the first solve and a re-solve of each solver's own accepted graph. Re-solving an already-solved graph approximates diagnosis cost but still includes parse/compile, convergence detection, mapping and validation. It is not an isolated diagnosis timer. Rejected first solves have no already-solved input, so their re-solve rows are skipped. Two edit sequences start from the same accepted PlaneGCS graph for both adapters: slot radius 3 to 3.5 mm, then to 4.2 mm, and adding then removing one released die dimension. Every accepted result feeds the next edit. Failed edits never become the next input.

Drag trajectories run every mode from the start (each frame from the trajectory's first accepted graph, as editor previews do) and chained (each accepted frame feeds the next). `die-slot` releases only the slot radius of the connected die, then moves its upper-left endpoint through 60 frames with a reversal; frame 45 targets an unreachable x coordinate, which is projected onto the remaining freedom. `arm` stretches a two-link arm out of reach and back over 47 frames, `four-bar` drags a four-bar linkage out of reach over 10 frames, and `tangency` approaches a tangency to 7.5e-6 mm and lands on it. Each group records outcomes, native drag outcomes (reached, projected, limited or stalled), which solver answered, the largest distance to a target, every frame's target and error, frame p50/p95/p99 and raw counts over 8 ms. Percentiles use `cadBenchmarkStats` nearest ranks. Frames are measured back-to-back without frame pacing or a rendering budget. The `sweep` section drags every point of the die and of the free die that the solver may move (both coordinates numeric, not pattern-generated or referenced) by a small, a large and an out-of-reach offset, once per mode, and counts drags that end further from their targets than the first mode's.

`totalMs` is the public-call total. `stagesMs` partitions it into `parseCompile` (including component preparation), `nativeCall` (wrapper/buffer work, native solve and PlaneGCS diagnosis), `mapping` (diagnostic source ids and geometry), and `validation`. Observer and promise overhead remain in totals; stage medians need not sum to the total median. The bundled PlaneGCS module logs some rejection paths directly to the console, and those paths retain that cost. The suite checks every accepted graph again outside timing and detects input mutation. Zero correctness failures means those geometry/integrity checks passed; diagnosis agreement is checked by the tests above.

Use the existing 1.5-times calibration drift rule. Each workload/edit sequence and drag trajectory group records before/after calibration; capacity pairs also have brackets. The cold section brackets all its processes once and is marked `THROTTLED` like any group. A `THROTTLED` group is unsuitable for a latency comparison even if its geometry is correct. Cross-group comparisons also need similar calibration, and cross-host comparisons remain invalid.

### Resource measurements and limits

- Cold probes run in a separate Node process each, with the parent's Node flags, to avoid V8 WASM compilation-cache reuse. The module breakdown records local file read, explicit `WebAssembly.compile`, instantiation/glue and their sum, plus raw/gzip WASM bytes. First-answer probes time loading through the first answer for four scenarios: PlaneGCS alone, native only and native first on the die, and native first on `overlapping-conflicts`, where it must also load PlaneGCS. The input is built before the timer. OS disk caches are not flushed. Browser/network fetch time, download caching and browser cold startup are unavailable here; a local file read is not a network benchmark.
- Each workload's memory probe uses a fresh instance and records `WebAssembly.Memory.buffer.byteLength` before and after the solve. This is retained linear-memory capacity, a high-water allocation, not live allocator usage. It remains useful when C++ or Rust allocations are freed. Node RSS, JS heap, external-memory and ArrayBuffer deltas are sampled at the call boundaries. GC is uncontrolled and deltas can be negative; they are not attributable peaks. Temporary process-allocation peaks are unavailable while the synchronous WASM call runs.
- The repeat probes seed an accepted die and re-solve it 1000 times in the same instance, then run the die-slot frames from the start 1000 times in another. Memory is recorded after 1, 10, 100 and 1000 calls, with native instance resets and whether PlaneGCS loaded. For `native-first`, WASM capacity sums native and PlaneGCS once both are loaded. Independent checks happen outside solving, so process deltas also include checker allocations. This does not measure a succession of different large workloads.
- Capacity uses connected rectangle chains, three public solves per candidate in fresh initialized instances, and the median total below 1000 ms. `planegcs` and `native-only` receive the same candidate; `native-first` is left out, as a group native refuses as too large is also too large for PlaneGCS. Both receive it, in alternating order within each bracket. It brackets then binary-searches the integer boundary, up to 4096 rectangles. The report retains every acceptance, rejection, calibration and sample. A result at the search cap is a lower bound. A boundary is throttled when the calibrations of its two probes, taken together, differ by more than 1.5 times; it is flagged in the limit and console summary, alongside the largest unthrottled solved probe. Timing noise near one second can move the measured boundary; it is not a product limit. PlaneGCS's 500,000 parameter/equation product guard remains authoritative even when a larger solve might be fast enough. Native capacity includes diagnosis from 0.0.742.

The historical baseline above is unchanged. There is no committed solver baseline JSON to regenerate. New full-run measurements belong in the release-specific table below; retain their JSON/Markdown reports with review evidence.
