# Startup imports and test environments

The browser must initialize and validate its cache workbench before optional actions run. Stored post and machine schemas, exact package hashes, binding validation and transaction recovery remain on the eager startup path. Do not defer those checks or treat a previously installed package as trusted merely to shrink a bundle.

Application services load complete machine-package preparation/installation, controller artifact generation and saved-revision deletion when invoked. Their signatures and domain implementations are unchanged; injected test services still use the same interface. Post installation loads its conformance fixtures/runtime after hash and duplicate checks, while stored-library reads continue to validate immediately. Lightweight package input limits and in-memory installation freshness checks live apart from the archive/execution code. Existing public domain exports remain available.

For production comparisons, count the JavaScript entry, every modulepreload and their recursive static imports. A smaller entry alone can hide transferred code in shared chunks. Using the same installed dependencies, the recovery release 0.0.693 build and integrated 0.0.694 candidate measured 943,343 versus 884,876 raw bytes and 271,604 versus 256,755 gzip bytes in that closure (6.2% and 5.5% lower). These counts exclude dynamic imports, workers, CSS, images and WASM. They describe initial JavaScript transfer, not total application size or a measured startup-time improvement. First use of a deferred action still fetches its code; module-loading failures propagate through the existing action error handling.

Vitest has two mutually exclusive projects. `pure-domain` runs compensation, execution-plan, path-editor, path-intel and simulation suites in Node without the browser setup file. `browser` runs every remaining suite in its existing jsdom environment with the Web Locks shim. Storage, package, editor persistence, File/download and UI tests stay in that browser project. New tests in the pure folders must remain independent of browser globals; move browser-dependent tests into a browser-owned folder rather than adding browser shims to the pure project.

`npm test -- --run` still selects the complete suite. Use `--project pure-domain` or `--project browser` to select one environment, and bound workers when comparing performance. No assertions or timing thresholds change with the environment split. Sequential same-host probes of the same 42 files/346 test identities measured passing jsdom/Node runs at 14.94/7.79 seconds with four workers. An earlier jsdom control failed an existing timing ratio; preserve that evidence rather than relaxing the assertion. This is illustrative subset evidence, not a whole-suite or CI speed guarantee.

Cold Chromium acceptance must still exercise browser-cache startup, real DXF processing, complete machine-package installation and saved controller output. Domain tests alone cannot verify that a deferred production chunk loads correctly. UPID, post schemas/capabilities, execution events, engine API, output/audit rules, installation semantics and storage formats are unchanged by these import boundaries; no installed package or saved revision is rewritten.
