## Three highest-value next workflows

| Order | Human workflow still missing | Why it matters now, and a useful boundary |
| --- | --- | --- |
| 1 | Click the middle portion of a crossing edge to remove it, keep both outside pieces, then reconnect and build. | Current end Trim explicitly throws `unsupported-sketch-trim-middle`; manual Split/Split/Delete requires multiple picks and separately owned edits. Completing this ordinary S16 behavior directly extends the tool already in use. Start with middle **line** Trim, explicit survivor IDs and support intent; arc/circle middle Trim and arc Extend remain separately unaccepted. |
| 2 | Create an inset/outset clearance or wall loop at a typed distance. | S17 Offset is wholly absent from the sketch edit union and UI. This is particularly useful in a wire-EDM authoring app, while remaining distinct from installed-post machining compensation. First support exact simple line/arc loops, a visible side and an explicitly independent copy. Reject collapsing/self-intersecting results; do not advertise an associative offset without its persistent dependency model. |
| 3 | Select and Pad the visible lens/lobes of overlapping circles, or the cells of a divided planar profile. | `cadSketchGraphGeometry.ts` deliberately withholds crossing/branched material components, so visible bounded areas can still yield no material. Existing region selection does not supply these cells. This is a substantive material workflow, but it requires reviewed cell identity, partial-source boundaries, holes/shared-edge union and downstream references. Treat it as its own integration, not a switch enabling the isolated arrangement file. |

This order favors complete everyday results using existing ownership. It does not downgrade the other baseline requirements. Ordinary Tangent, associative midpoint/concentric/symmetry relations, calculated reference dimensions, stable projection/reference reuse and sketch mirror/pattern still need acceptance. The original reference classifies those line/arc sketch operations separately from optional splines, 3D sketches or automated constraint suggestions. Body patterns do not satisfy sketch S19; position-only legacy snaps do not satisfy associative S18.

Official behavior supports the first two workflows, without dictating our identity policy. Onshape Trim removes to the first intersection and deletes a curve when no boundary exists; Fusion documents live Trim/Extend previews and next-intersection behavior. FreeCAD's official documentation also describes middle removal, transferred applicable constraints and point-on-object contact. We must not claim that last attachment behavior for our numeric intersection cuts. [Onshape Trim](https://cad.onshape.com/help/Content/Sketch/trim.htm), [Fusion Trim/Extend](https://help.autodesk.com/cloudhelp/ENU/Fusion-Sketch/files/SKT-TRIM-EXTEND.htm), [FreeCAD Trim source](https://github.com/FreeCAD/FreeCAD-documentation/blob/main/wiki/Sketcher_Trimming.md)

Onshape Offset documents selected curves/loops, typed distance and direction, including negative values for changing side. Our initial independent-copy policy would be an authored scope choice, not a claim of matching every vendor association rule. [Onshape Offset](https://cad.onshape.com/help/Content/Sketch/offset.htm)

## Recommend middle line Trim next

One complete slice should let a person right-click an actual source line between two finite transverse boundaries, see the middle removal and both survivors, and accept one edit. The equivalent hosted agent obtains the same witnessed proposal and submits the same operation. Keep current pointer ownership, one accepted Undo, private consumed-sketch editing and explicit area repair. Do not add a persistent Trim mode, numeric cut panel or automatic cutter noding.

The geometry query already has most of the required math. `cadSketchTrimExtend.ts` computes source-parameter-sorted finite events, validates transverse contact and declared endpoint witnesses, then rejects a pick inside the first/last event. For middle removal, find the adjacent pair immediately bracketing the chosen parameter, not the outermost intersections. Reuse `boundaryEvents`, range checks and partition/support validation. A pick on an intersection, ambiguous undeclared ties, overlap, tangent or degenerate remainder must remain unavailable. Four fences are an important case because removing the entire span from first to last would be wrong.

Add a strict `middle` arm to the existing Trim target, initially requiring an actual line. It needs two ordered boundary witnesses, two explicit cut-point IDs, a new survivor entity ID and a support-relation ID. Each cut reuses an existing endpoint only when its witness explicitly names that exact endpoint, otherwise it receives a fresh numeric point. Allocate all identities once for the owned preview. Retain the old line ID on source range `[0,t0]`; the named new line owns `[t1,1]`. Retain old outer endpoint IDs, every old point/scalar and construction flag. The removed interval is `(t0,t1)` from the original source support. Array reorder must not change these witnesses or identities. A reversed source has its own source-start convention; screen left/right must not choose which child keeps an ID.

### Real support dependency

Two disconnected survivors cannot be kept on the same infinite line with Parallel alone: they can slide onto different parallel supports. Existing Split avoids this because its children still share their cut point. Middle Trim removes that joint. Do not silently freeze new numeric points, invent a hidden construction span, or claim a loose pair of parallel pieces preserves one original support.

The lean persistent support is one scalar-free `collinear` relation with the existing line-pair shape `{ id, kind: 'collinear', lineIds: [retained, new] }`. The pinned package has `parallel` and `point_on_line_pl`/`point_on_line_ppp`, so it can express direction plus one endpoint on the other's support without a binding/rebuild. There is no typed `collinear` package constraint in the current declarations. One composed relation is clearer than leaking an invisible native equation into the source. It owns two independent scalar conditions for ordinary disjoint free lines.

This is a proposed source addition, not native runtime proof. Independent acceptance must check the existing strict angular direction contract and world support distance using the approved driver policy. Wrong fixed coordinates must reject even if native Success omits conflict IDs. No new tolerances, solver tuning, projection or JS correction. The relation is inspectable/removable like Split's structural support relation; removing it deliberately releases shared-support intent. It need not become an unrelated constraint-palette expansion before Trim works.

Middle Trim preserves both original outer endpoints, unlike end Trim. Point relations on those endpoints can therefore remain byte-for-byte unchanged: a distance between the old outer endpoints still measures their span across the removed gap. Original endpoint-pair H/V also retains its exact point meaning, and collinearity carries that orientation to both survivors without operand substitution. An existing Parallel/Perpendicular whole-line direction can retain the old ID's relation because collinearity carries the same support direction to the new piece. Equal length, explicit endpoint-ray angles, corner treatments and other whole-edge size/sector owners cannot silently change to a shorter survivor. Block them with actual source subjects until an explicit transfer rule is authorized. Verify these policies rather than copying end Trim's detached-endpoint blockers wholesale.

The cuts remain one-time numeric contact with a cutter interior. They gain no point-on-cutter relationship and do not follow cutter edits. A witnessed actual endpoint can share its declared point ID. Neither contact policy creates material cells automatically; a remaining T-junction/branch still has the production compiler's existing limits.

## Meaningful acceptance, before claiming delivery

1. **Exact geometry and identity.** A source line with four finite cutters removes only the span surrounding the pick and preserves both outer pieces. Reorder entities and reverse source orientation; verify the exact physical removal, stated retained-ID convention, both endpoint witnesses, old scalars and source bytes. Include endpoint reuse, a nearby distinct point and an unrepresentable/degenerate candidate. None may become proximity healing or deletion of unrelated pieces.
2. **Persistent support and ownership.** Real pinned solving keeps disjoint survivors collinear through one ordinary parameter/point edit, with correct freedoms. Preserve a fresh rectangle's H/V and old outer-point drivers exactly; block actual finite-length/ray/corner owners. A fixed incompatible collinearity and an injected cut/cutter drift reject the entire candidate. No repeated tuning or broad numeric matrix.
3. **Complete human and agent result.** Start a consumed plate edit, remove a middle line span, reconnect it to retained exact points, approve changed areas when needed, and Finish once. Preview/Cancel, local Undo/Redo, whole-part Undo, source/frame replacement, aborted late completion and save/reopen preserve the correct versions. The same witnessed agent proposal/edit/repair gives structurally equivalent source and a real measured solid. Prefer extending an existing consumed-Trim journey over creating many similar journeys.

## Why Tangent, references and material cells are not folded in

Tangent remains a high-value unfinished relation: [Onshape](https://cad.onshape.com/help/Content/Sketch/tangent.htm) documents it between curve pairs, and the original matrix expects persistent line/arc intent. The [bounded six-solve preflight](2026-10-16-sketch-tangency-plan.md#bounded-native-preflight-six-solves-unchanged-acceptance) found a real ordinary radius `5 → 8` edit that fails both tangent and strict structural-radius checks despite native Success. Free/fixed successful examples do not establish reliable everyday parameter editing. Keep that actual limit visible; do not repeat conditioning/native-memory investigations, loosen structure or ship a general Tangent promise from the two successful seeds.

Stable/generated references remain distinct from the frozen position-only snap slice. A transient plugin boundary index cannot become a saved reference after regeneration. Source-owned anchors, broken-reference recovery and cross-plane projection need their own S18 contract. For intersecting cells, `CadSketchCellReference` currently owns whole cycles and nesting, not oriented source subranges; the isolated arrangement's candidate keys are not a reviewed persisted reference format. Its existence is useful prior work, not acceptance evidence. Integrating any of those into middle Trim would obscure its source/history guarantees and substantially enlarge the slice.

Calculated reference dimensions, sketch mirror/pattern, arc/circle Trim/Extend, ordinary tangent/arc interaction and direct API enumeration of generated reference points also remain open. The next checkpoint should report exactly the accepted middle-line workflow, then return to this list. None of these priorities justifies marking the overall sketch goal complete.
