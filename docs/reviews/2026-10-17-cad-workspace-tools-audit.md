## Recommended next repair: useful Section for CAM defaults

**Confirmed source-backed friction.** Create an ordinary XY Pad from Z0 to10, choose File → Section for CAM, then Preview section without editing its fields. [CadSectionDialog.tsx:45–47](../../src/features/cad/CadSectionDialog.tsx#L45) initializes XY and literal offset `0`. [cadKernelSection.ts:19–26](../../src/features/cad/kernel/cadKernelSection.ts#L19) rejects a section on or outside the body bounds. This first request necessarily fails for that Pad; raised stock Z5–10 starts outside too. The failure is safe, but the app asks the user to repair an avoidable initial request. Existing dialog tests currently mock a successful result for request offset0, so they do not establish this ordinary first-preview outcome.

DXF's Solid section already initializes at the selected body's midpoint, using [middleOffset](../../src/features/cad/CadDxfExportDialog.tsx#L29). It also recalculates on deliberate body/plane replacement. Reuse that behavior:

- Extract only that small pure helper into a leaf module shared by both dialogs. Do not import the DXF component into the CAM component, since DXF already imports `CadSectionPreview` from the CAM dialog.
- CAM's body prop currently keeps only featureId/name. Include bounds; [App already passes full meshes](../../src/App.tsx#L181), so production plumbing needs no new model/query. Initialize from the chosen body. On explicit body/plane changes choose its midpoint along +Z, −Y or +X respectively.
- Keep an authored offset during unrelated rerenders. Preserve the exact request key, mandatory Preview before Send, cancellation, storage receipt and version guards. A midpoint is a useful starting point, not a claim that every nonconvex or multipart body has material there. Native validation stays authoritative.

Meaningful verification after authorization: update the existing mounted preview/review case to supply real bounds and expect XY5 for Z0–10; add one raised-body or XZ sign case, preserving custom offset across rerender. Then one actual raised Pad → first Preview → CAM handoff proves the avoided error and unchanged section geometry. No tolerance, kernel or storage schema change is needed.

## Important existing interaction limit: replacing topology seeds

**Source-confirmed affordance gap, not a demonstrated regression.** Reopen an existing selected-edge Fillet/Chamfer and try to change which edges it treats, or reopen Shell and choose a different opening. [CadFeatureEditor.tsx:135,277–293](../../src/features/cad/CadFeatureEditor.tsx#L135) offers the originally captured selection or all-body scope; Shell exposes a read-only query summary. Body replacement retains the old geometric query. Radius/thickness editing works, but there is no in-editor repick action. The query may still match a deliberate compatible replacement body; do not call every body change invalid or erase its selector automatically.

This deserves a separate bounded workflow, not a button that picks the wrong build. The selected operation consumes its input body, so the final viewport normally contains the result. [cadTopologyActions.ts:21–28](../../src/features/cad/cadTopologyActions.ts#L21) correctly requires the requested body in the current visible build; the worker also requires the exact cached document/build pair. Relaxing these checks would be wrong.

The smallest credible reuse is an owned **Choose edges/opening** stage within the existing feature reference picker. Clear the operation preview first, build the strict history prefix preceding the edited feature in the existing isolated preview worker, and display/pick only the target input body. Resolve picks using that same worker/document/build, then return only the ordinary persisted geometric selector to the existing feature draft. Existing fieldset locks, token/version checks, cancel restoration and full-part prepared preview/Apply remain. It needs one narrow topology-pick command arm and a preview-client resolve callback, not a global selection/cache service. The current preview client type exposes only build/dispose, so this is real integration work.

Before implementation, pin the same prefix inspection contract for existing public topology tools, so agents can obtain the identical selector rather than fabricate predicates. A focused proof should edit a consumed Fillet seed and Shell opening, preserve feature ID and untouched fields, Cancel back to the old selector, reject a stale prefix/build, then Apply/Undo/save. No native feasibility experiment is indicated by this source read, but the owned-prefix route has not been exercised. Do not bundle it with the section-default repair.
