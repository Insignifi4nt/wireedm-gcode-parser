# CAD local resource audit

Audit date: 2026-10-14. Repository baseline: `09795ec5e0e404f5ce69ff2173dea119a69f66ce`, with concurrent uncommitted CAD capacity changes. This private engineering record traces portable CAD, source imports, saved CAD, native exports and shared cache/folder transactions. Line references and source hashes describe this snapshot; they are not stable identifiers across later edits.

## Findings and scoped repair

### A shared journal policy could still make a valid accepted CAD document unsavable

Removing the CAD-specific 4 MiB policy alone was insufficient. `workbenchFileTransaction.ts` independently rejected its serialized recovery journal above 384 MiB, both when committing and recovering. An ordinary CAD save uses this transaction. The journal includes exact previous and next saved-file text, escaped as JSON string values. Its size therefore exceeds their sum: backslashes, quotes and control characters require further escaping. Updating two approximately 192 MiB ASCII files could exceed the policy; highly escaped data reaches it earlier. This was an application rejection, independent of folder capacity or the native kernel.

A test written before repair failed with `File recovery data exceeds its size limit.` It uses 64 MiB of logical NUL text, which JSON encodes into a real recovery envelope above 384 MiB; it does not falsify a byte count or mock the old constant. The generic file transaction is the subject, rather than claiming that raw NUL text itself is a valid CAD document.

The write/recovery byte gates are removed. The same schema-version-1 journal, portable paths, maximum 10,000 file records, duplicate/case collision checks, `expectedPrevious` comparison, exact readback, rollback rules and index ordering remain. Cancellation still runs at the final guard before the journal write. Once that write starts, the transaction finishes or retains recovery evidence. No migration, sidecar format, cleanup inference or journal deletion policy was introduced.

The large regression now commits exact contents, survives an interrupted committed-journal cleanup, reopens/reconciles that journal, removes it only after verifying committed state and rejects a conflicting optimistic write. Existing cache/folder cases cover interrupted writes, rollback, unexpected external changes, cancellation before writes and retries.

### Exact saved-file reads lost cancellation when their bounded byte policy was removed

Previously `readExactText(path)` had no signal in either adapter. Folder reads allocated the complete byte buffer; cache reads expanded the complete gzip output with fflate. Moving CAD from the bounded reader to that ordinary exact reader would remove the size policy but lose cancellation during the read/decompression.

The compatible API is now `readExactText(path, signal?)`. `exactTextStream.ts` exports `readExactUtf8Blob(blob, signal?)`, also used by the portable JSON import owner. It prefers `Blob.stream()`; older Blob implementations use 64 KiB slices. A fatal streaming UTF-8 decoder retains a leading BOM and incomplete multibyte characters between chunks. Abort cancels a pending reader, discards partial text and releases the lock/listener. Plain cached strings are checked for malformed UTF-16 before an exact UTF-8 claim is made; they are never rewritten. The separate bounded logical recovery reader still captures malformed plain-cache code units truthfully.

Compressed cache reads decode base64 in chunks, avoiding a complete binary base64 string and expanded byte array. Native `DecompressionStream` is preferred. Its absence uses incremental pinned fflate `Gunzip` with a cooperative task yield for each 4 KiB base64 chunk, preserving previous cache usability without new worker infrastructure. fflate does not verify gzip footers itself, so the fallback validates every member's CRC/ISIZE against the original envelope. Both paths preserve concatenated complete members, BOM and UTF-8 text, reject corrupt checksums/invalid encoding and leave stored originals untouched. There is no logical file-size ceiling or `Infinity` stand-in in this exact-reader API.

This repairs one read allocation/cancellation boundary. Returning a full string still requires complete decoded text; joining chunks and subsequent JSON parsing still allocate. A synchronous plain-cache lookup/Unicode scan cannot be interrupted halfway by another main-thread event.

The installed native loader's heap-growth expression clamps to `4294901760` bytes and its application mesh pointers use `pointer >>> 0` against the current `wasmMemory.buffer`. These are concrete 32-bit address/memory boundaries in the installed build. Allocator failures or native index overflows can occur earlier; the application must reject invalid pointers/counts. They do not explain the much smaller application topology/facet/byte policies. No test here promises that a browser can allocate that maximum heap.

`browserCacheAdapter.ts` still uses full `strToU8` for compression, asynchronous fflate input without its consume/transfer option, base64 text conversion and synchronous localStorage writes. The fallback without Worker still compresses synchronously. The new exact-reader removes complete decode byte buffers, but it does not fix compression/storage copies. Replacing localStorage payloads with IndexedDB Blob records or OPFS is the larger cache improvement; existing exact data requires a verified, retryable migration, not a silent rewrite.

## Recommended implementation order and meaningful cases

1. Finish the immediate coordinated policy/reader repairs and parent worker-lifetime/clone work. Re-run compact JSON import/export, source import above former 2 MiB, saved CAD above former 4 MiB and journal above former 384 MiB. Verify exact original hashes, fresh imported identities, no partial acceptance, cancellation, both adapters and unchanged receipt after conflict/interruption.
2. Measure live edit/query/save/export on low-topology originals at 8/32/128 MiB, including compressible and high-entropy payloads. Record main-thread stalls, peak resident memory, encoded/decoded bytes, request copies and native heap behavior. Use a small independent solid as the material fixture so size policy is not confused with topology/meshing cost. Benchmarks should not become arbitrary acceptance gates.
3. Remove one proven extra copy at a time: journal exact readback, exported FS bytes, validated kernel request snapshot, preview typed-buffer transfer. Test mutable input after queueing, stale publication, active/queued Abort, current cached picks, failed read-only query retention and worker cache buffers remaining undetached.
4. Introduce an internal immutable original registry and small worker document/source tokens. Test exact hash collision/error handling, shared-source references, version changes without source changes, reopen/portable flattening, cancellation and detachment. Keep the external portable document schema unchanged unless a separately reviewed version is justified.
5. Review a staged transaction/cache format only after measurement shows the current monolithic journal is the bottleneck. Test every interruption point, exact old/new images, conflicting backups/staging paths, original preservation, cross-tab scope, outside folder edits and retries. Include legacy journals in migration tests. Cleanup requires known ownership and an explicit safe protocol, never absence of catalog references alone.

## Cross-system Simulation-to-editor Save follow-up

The parent's full browser run exposed an existing app workflow test that expected `Saved` immediately after a click and the helper's two microtask flushes. The isolated original command reproduced `Saving` instead. Streaming exact reads perform real asynchronous I/O; those microtask flushes do not wait for its durable transaction receipt.

The test now observes the real `saveEditorProgram` operation through the existing AppServices seam and awaits its actual result inside React `act`. No fake save, production fast-path bypass, fixed delay, timeout increase, controller change or weaker geometry assertion was introduced. The complete Simulation-to-editor path runs with real cache and folder adapters. Both cases verify immediate return to the editor, one save operation, successful durable receipt, `Saved` UI, translated X=3 in persisted geometry and returned editor data, receipt/project agreement, byte-for-byte unchanged DXF original and a cleared recovery journal. A guard or storage failure cannot satisfy those assertions.

The repaired app suite plus editor save/concurrency suites passed **16 tests in 3 files**. All five frozen shared source hashes were rechecked and remain unchanged; the issue was premature test observation, not loss or corruption of the dirty draft. The parent re-runs the full browser gate after the other independent fixes freeze.
